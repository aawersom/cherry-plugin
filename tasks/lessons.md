## 2026-10-07 (вечер) — миграция на Lampa.Maker, Lampa 1.13.3, прогрессивный поиск (v0.13.27)
- Устаревшие API Lampa видны только в консоли («Component InteractionCategory is deprecated»). Замена не документирована — её нашёл исходник lampa.mx: `Lampa.Maker.make('Category')` + модули + `card.use`. Правило: при каждом обновлении Lampa grep консоли на `deprecated` и экспорт `window.Lampa`.
- Миграцию сделал адаптером под ОДНИ хуки экрана (Maker + легаси), а не переписыванием экранов — логика Cherry не менялась, тесты перепривязаны к тем же гарантиям.
- Маска модулей карточки задаётся на элементе ДО создания карточки (`Create` создаёт инстанс раньше `onInstance`), иначе сыпятся бейджи TMDB и чужое long-press меню; модуль `Release` нужен даже без года — он убирает `{release_year}`.
- adb `--longpress` короче 800 мс → Lampa видит обычный Enter; long press проверять через `Lampa.Controller.long()` (тот же путь, что вызывает Lampa после удержания).
- Официальные APK Lampa без отладки WebView — CDP невозможен; проверка «как пользователь» (adb-клавиши + скриншоты) достаточна для совместимости. Пересборку APK с debuggable и постоянный FlareSolverr на VPS политика безопасности блокирует — это решения владельца.

## 2026-10-08 — синхронизация поиска (v0.13.28)
- ИКР сработал: прежде чем менять сервер, прочитать его merge — `mergeFavs` хранит записи целиком и склеивает по `id@source`, значит новый тип данных едет в том же бакете с зарезервированным `source`. Ноль серверных изменений при заблокированном деплое воркера.

## 2026-10-08 — стенд пишет в РЕАЛЬНЫЙ бакет владельца
- На стенде стоит рабочий PIN владельца (`cherry_sync_pin`), поэтому любое открытие Cherry с тестовыми данными синхронизирует их в настоящий бакет. Проверка v0.13.28 (подложенная старая история) отправила 2 записи `__rq` в бакет владельца, а его ТВ на 0.13.27 показал бы их пустыми карточками избранного. Исправлено tombstone-записями (`deleted > added`, старые клиенты их скрывают), локальная история стенда очищена.
- Правило: перед тестом синхронизации на стенде ставить одноразовый PIN (`Sync.setPin`) и возвращать рабочий после; никогда не подкладывать тестовые записи при рабочем PIN. Проверять бакет до и после (POST с `{"records":[]}` и браузерным User-Agent — без него CF отвечает 403).
