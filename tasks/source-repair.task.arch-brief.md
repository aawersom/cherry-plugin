## 1. Architectural Invariants That Apply to This Task

### INV-1 — SOURCES registry integrity
`SOURCES[]` is the single source of truth. All three adapters under repair already have entries. No adapter is being added or removed; `SOURCES.length` stays 25. No count guards in the E2E harness change.

### INV-2 — Proxy layer is the only external HTTP path
All outbound requests must route through `cherryFetch` / `cherryPost` / `proxyM3u8`. The single exception allowed in the current codebase is `_apiFetch` on the Eporner adapter — it uses raw `fetch()` because the Eporner JSON API carries `Access-Control-Allow-Origin: *`. The fix to `getStream` removes this exception for video page fetches; the exception survives only for the two JSON API calls (`search`, `browse`).

### INV-3 — `buildProxyUrl` hostname routing is the authoritative proxy selector
The host-to-proxy mapping lives in `PROXY_URL_2_HOSTS`. Adding a hostname there is the only permitted way to switch an adapter's traffic to Deno Deploy. The SpankBang fix requires adding `ru.spankbang.com` to this map (see Section 4 — Risk).

### INV-4 — Single-file IIFE; no module split
All changes land in `plugin.js`. Helper functions must remain at the correct lexical scope. No new module-scope variables unless they serve multiple adapters.

### INV-5 — `plugin-release/plugin.js` must be kept in sync
After every edit to the main `plugin.js`, the same change must be applied to `plugin-release/plugin.js`. This is a mechanical sync step; the spec must make it explicit.

### INV-6 — Adapter output contracts are frozen
`BrowseResult`, `VideoCard`, and `StreamResult` shapes must not change. The SpankBang fix changes how cards are fetched (different domain) but must produce `VideoCard.url` values pointing to `ru.spankbang.com` consistently so that `getStream` can fetch the same domain.

## 2. Patterns That Must Be Preserved

**SourceAdapter interface.** Each adapter exposes exactly `{ id, name, host, search, browse, getStream }`. No new public properties.

**Proxy routing via `cherryFetch`.** Never call raw `fetch()` for HTML page scraping. The Eporner `_apiFetch` pattern (raw fetch for CORS-open JSON APIs) is a named exception; it must not be extended to HTML endpoints.

**`extractStreams` as shared fallback.** Where a dedicated parser fails, falling through to `extractStreams(html)` is the established pattern. New stream parsers should follow the same fall-through discipline.

**`cherryPost` for POST stream APIs.** SpankBang's existing `getStream` uses `cherryPost` for the `streamkey` path. If the new HTML-based quality map path is added as the primary strategy, `cherryPost` remains as a fallback or is kept for parity. Do not remove it unless the new path is proven to be strictly superior.

## 3. What the Spec Writer Must Know About the Proxy Layer

**Two proxies, one selector function.**
`buildProxyUrl(url)` reads `new URL(url).hostname` and checks `PROXY_URL_2_HOSTS`. If the hostname is listed, the request goes to Deno Deploy (`cherry-proxy.aawersom.deno.net`); otherwise to the CF Worker (`cherry-proxy.aawersom.workers.dev`). The spec writer does not need to touch `buildProxyUrl` itself — only the host table.

**Deno Deploy limitations.**
Deno Deploy bypasses CF ASN-level blocks but does NOT bypass Cloudflare JS challenges. `spankbang.com` and `www.spankbang.com` are in `PROXY_URL_2_HOSTS` today yet still fail because SpankBang's CF challenge fires on all datacenter IPs including Deno's. `ru.spankbang.com` reportedly avoids this challenge (orchestrator pre-analysis). Adding `ru.spankbang.com` to the host table follows the established pattern for xnxx.

**Existing `PROXY_URL_2_HOSTS` entries relevant to these three adapters:**
- `spankbang.com`, `www.spankbang.com` — already listed, still fail (JS challenge)
- `www.pornhub.com` — already listed (Deno proxy); the PornHub embed fix must ensure the embed URL's hostname (`www.pornhub.com`) also resolves through Deno
- `www.eporner.com` is NOT listed — video page fetches currently use raw `fetch()` (no proxy). Adding `www.eporner.com` to the host table OR calling `cherryFetch` (which auto-routes through CF Worker) are both valid; the CF Worker approach is simpler.

**PornHub embed URL hostname.**
`/embed/{viewkey}` is served from `www.pornhub.com`. That hostname is already in `PROXY_URL_2_HOSTS`, so `cherryFetch('https://www.pornhub.com/embed/...')` will automatically route through Deno Deploy. No host table change is needed for PornHub.

## 4. Architectural Risks From the Proposed Fixes

### SpankBang — CRITICAL CONFLICT WITH ARCHITECTURE DOCUMENT
The orchestrator pre-analysis states `ru.spankbang.com` works via Deno proxy (200, 607KB HTML). **CHERRY.md Section "Source Status" currently records SpankBang as unfixable** — "Cloudflare JS challenge on all paths; blocks CF Worker and Deno Deploy equally."

These two claims are contradictory. The spec writer must resolve this before writing requirements:

- If `ru.spankbang.com` genuinely bypasses the challenge (different CF configuration on the Russian subdomain), the fix is valid and `PROXY_URL_2_HOSTS` must gain `'ru.spankbang.com': 1`.
- If the orchestrator's finding is a false positive (e.g., a cached response, or the challenge is intermittent), implementing the fix will produce 0-card results in production.

**Recommended action before spec:** add a live verification step as a prerequisite gate. The spec should not proceed to implementation for SpankBang until the Deno proxy returns consistently populated HTML from `ru.spankbang.com/new/1/` on two separate requests.

Additionally, the adapter's `host` field should be updated from `'spankbang.com'` to `'ru.spankbang.com'` to reflect the actual origin in use, so that operator logs and UI are honest.

### PornHub embed — low risk
Switching from `view_video.php` to `/embed/{viewkey}` is a targeted change to one function. Risk: the embed page HTML structure (flashvars / mediaDefinitions) must match what the current parser expects. The parser already handles this format (it is the existing production pattern). Risk is low if the regex is tested against a real embed page sample before commit.

### Eporner — PROXY_URL_2 routing decision
Switching `_apiFetch` calls in `getStream` to `cherryFetch` means video page fetches go through the CF Worker (since `www.eporner.com` is not in `PROXY_URL_2_HOSTS`). The orchestrator states the Deno proxy returns 97KB pages with the hash present; it does not state whether the CF Worker also works. The spec must clarify which proxy is used. Adding `www.eporner.com` to `PROXY_URL_2_HOSTS` is safe but unnecessary if the CF Worker passes; adding it only if CF Worker is confirmed to fail avoids over-engineering.

### URL format change for Eporner
The orchestrator notes the URL format shifted from `/hd-porn/{id}/` to `/video-{id}/{slug}/`. The API's `v.url` field already returns the correct current URL. The `_mapVideo` function builds `url` from `v.url || ('https://www.eporner.com/hd-porn/' + v.id + '/')`. The fallback construction is now stale. The spec must patch the fallback to `/video-{id}/` or drop it if `v.url` is always populated in practice.

### `_apiFetch` partial survival
If `_apiFetch` is kept for browse/search (CORS-open JSON API) but replaced by `cherryFetch` in `getStream`, the function's doc comment must be updated to reflect this split. Leaving the comment unchanged creates false confidence that `eporner` "uses direct fetch throughout."

## 5. Whether HQPorner Status Should Update the Architecture Document

Yes. The architecture document must be updated. The current `CHERRY.md` section "Browse works, video broken (CDN architecture limitation)" already correctly records HQPorner's bigcdn.cc block. However, the architecture document's adapter table (Section "Source Adapters — Full List") still describes HQPorner's protocol as "HTML → mydaddy.cc embed → bigcdn.cc CDN" without noting that this chain is permanently broken.

**Required update to CHERRY.md:**
- In the adapter table row for `hqporner`, add a note: `(stream broken — bigcdn.cc CDN unreachable from all proxy tiers; not fixable without residential relay)`
- No code change to the hqporner adapter is warranted. The adapter should remain in SOURCES with its browse functionality intact. Removing it entirely would silently drop browse cards that currently work.

The spec writer should include a CHERRY.md update task as an explicit deliverable of this task, not an afterthought.
